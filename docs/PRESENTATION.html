Ask 2 · Context files

Your chat context is not the project's memory

A conversation ends and takes its context with it. A file does not.

Three people, multiple AI sessions, nineteen days. Anything that exists only in a chat log is effectively lost — and gets re-argued from scratch by the next session.

When this happensUpdate this

Ask 2 · Context files

Decisions Already Made — Do Not Re-Litigate

Agents re-propose rejected ideas fluently and confidently. So the reasoning is written down, not just the conclusion.

  • §4.1 — the official Garmin Health API is off the critical path. Partner approval, lead time we cannot schedule against 31 July.
  • §4.2 — workout and meal libraries are locally seeded, not runtime API calls. The whole demonstration runs with outbound network disabled.
  • §4.3 — there is exactly one scheduling engine. Rescheduling re-invokes it; it is not a second algorithm.
  • §4.9 — the system is not a medical device. It asks for a calorie baseline; it never estimates BMR.
We're not just documenting what we did. We're documenting what we decided not to do — because that's what an agent will otherwise undo.

Ask 2 · ★ The difference that matters

Same artifact, opposite ends of its life

The example pack

Contains finished .java files.

Written backwards from a program that already existed — so the output was pasted back in.

Ours

Contains requirements.

Written forwards to a program that did not exist yet. A prompt pack is a generator.

We conform to the house style — numbered in delivery order, a 00- summary, a phase map, and the five named techniques.

Run the pack in order and the agent creates the code. Re-running may produce different code — and that is expected.

Ask 2 · ★ Why the implementation must never enter a prompt

It breaks the measurement, silently

Paste the implementation into the prompt, and the tests start checking the code against itself. The coverage number stays green and stops measuring anything.

You don't find out — because nothing fails.

And a second cost: whichever way that one run happened to merge intervals or order its comparisons becomes the specification — indistinguishable from a requirement the team actually agreed on.

The claim this structure makes

Delete engine/src/, re-run packet 05, and the 30 frozen engine tests still pass.

The implementation is disposable. The specification and its executable form are not — which is exactly why the tests are written first (packet 04) and frozen before any implementation exists (packet 05).

Ask 3 · Structure

One engine, and it cannot cheat

engine/     findCandidateSlots()   pure · ZERO dependencies · 100% covered
shared/     contract.ts            human-authored, frozen before any agent ran
server/     reschedule/            WHEN the engine is called again
            recommendation/        metrics → decisions → real scheduled tasks
            api/  db/              Express · MongoDB
web/        React + TypeScript
  • Exactly one function in this system produces a placement. Rescheduling re-invokes it.
  • The engine has an empty dependency block, permanently — an engine that cannot import anything cannot import a clock.
  • Time is an integer Minute. The engine never sees a Date.

That purity is structural, not aspirational — and it is what lets the engine be property-tested over 1,000 randomized days with no database and no browser.

Ask 3 · Process

RED and GREEN are different agent sessions

RED agent          sees the SRS and the contract. Never an implementation.
   ↓
HUMAN GATE         a second person reviews. Nobody freezes their own suite.
   ↓
FROZEN             sha256 per file, committed
   ↓
GREEN agent        sees failing tests. MAY NOT edit, skip or weaken one — ever.
                   If it thinks a test is wrong, it STOPS and a human decides.

Why this can't be collapsed "for speed": when one agent writes the test and the implementation together, the test encodes what the code does rather than what the requirement says. It goes green, it looks reasonable, and it is wrong.

This is structural. It cannot be fixed by asking the agent to be careful.

~193 commits · 20 of them explicit RED/GREEN boundary commits.

Ask 3 · V&V

Two guards worth thirty seconds each

guard:single-placement

Ask an agent to repair the schedule when a commitment displaces a task, and it will write a tidy little findNextFreeSlot() inside the reschedule service — because that is locally the simplest thing to do.

The requirement is now false. No test fails.

$ npm run guard:single-placement
exactly one placement definition (findCandidateSlots, engine/src);
no PlacementResult-returning function elsewhere  (FR-RSC-03)

guard:tests-frozen

Hashes, not commits — a commit-based freeze needs the repository and that commit reachable. Hashes catch an edited test, an edited-and-committed test, a deleted test, and a file quietly added to a frozen suite.

Ask 3 · ★ V&V

A guard that has never been observed to fail doesn't count

Every guard is watched failing against a deliberately introduced violation before it is trusted.

Packet 16b produced 14 must-fail transcripts where 11 were required.

A green guard that enforces nothing exits 0 exactly like a working one. From the outside, they are indistinguishable.

This project has shipped that mistake twice and caught it both times — which is why the rule exists in writing rather than as good intentions.

Ask 3 · ★ V&V working — this week

What 507 passing tests did not catch

Rehearsing this demonstration yesterday, applying a recommendation to tomorrow's schedule returned "no workout above LOW to replace" — for a workout that had not started.

if (placement.start <= clock.nowMinute()) continue;   // ✗ no calendar in it

A minute-of-day comparison. Wrong in both directions: a future date's workout read as already begun; a past date's read as still upcoming — so a finished day's history could be rewritten.

Every frozen suite applies the recommendation to the clock's own date — the one configuration where the bug is invisible. We found it by running the system, not by running the suite.

Fixed with a date-aware check mirroring the one the reschedule service already had. Pinned by 3 new tests — 2 watched failing first. SRS corrected in place to v2.41. 510 green, all 8 freeze entries unchanged.

Ask 3 · The honest summary

Systematic testing tells you what you checked

It does not tell you what you forgot to check.

That is why we still rehearse against a running server.

Five levels are represented — unit, property, integration, contract, acceptance — using Jest, fast-check, supertest and mongodb-memory-server.

docs/TESTING.md records which tool was chosen for what, and the three that were costed and rejected — Postman/Newman, Vitest + RTL, Playwright/Cypress — so nobody re-proposes them.

Two fixed commitments — 09:00 lecture, 13:00 standup — and six flexible tasks the engine placed around them.

2 · Repair

Add a dentist appointment at 14:00 → Study CS4398 is displaced and re-placed at 15:00–16:30 by the same engine. Then try a second class at 09:00 → 409 — "That time conflicts with CS4398 Capstone Lecture."

Inject sleep score 40 → tier drops to LOW, calorie target rises → apply the workout → it becomes a real SYSTEM task placed by the same engine → drop a commitment on it and watch it get displaced like any user task.

Not a scheduler and a fitness app sharing a login. One system.

Where we fell short

The gaps, before you find them

  • FR-WEL-04 is not satisfied. The seven-day wellness panel was removed at the requirement owner's request. We flagged it, logged it as OPEN-37, and updated the SRS to say so — rather than let the document assert a capability the build no longer has.
  • No Conditional work was undertaken. Priority displacement, the live Garmin API, and the external content API are deliberately out of scope, recorded with reasons on 26 July.
  • Some late frontend work has no automated coverage — the wellness click-to-schedule path and the background sweep. Flagged rather than implied.
A stale document is worse than no document, because it is trusted.
