01The method: persistent context and incremental packets

The method has two halves: a master context document that never goes stale, and a sequence of incremental prompts derived from it. The first prevents drift across sessions; the second keeps any single session inside what a model — and a human reviewer — can actually hold.

The persistent knowledge base

CLAUDE.md sits at the repository root and is loaded automatically at the start of every agent session. It carries six things:

  1. Domain knowledge — what a task, an occurrence, a placement and a schedulable day are, and how they relate.
  2. System architecture — every component, its dependencies, and the module seams work is allowed to follow.
  3. Quantitative success thresholds — 90% engine line coverage (NFR-MNT-01), 1,000 property cases with no overlapping placement (NFR-COR-01).
  4. Baseline requirements that must survive every increment, including the one the whole project is built around (FR-REC-04).
  5. Technical specification — the contract types, the Minute time convention, the priority scale, the constraint that the engine declares zero dependencies.
  6. Decisions already made, each with the rejected alternative and the reason it was rejected.
The section that earns its keep

§4 of CLAUDE.md is titled "Decisions Already Made — Do Not Re-Litigate." It exists because an agent re-proposes a rejected idea fluently and confidently, and a tired human accepts it. §4.1 records that the official Garmin Health API is off the critical path — gated behind a partner-approval review with a lead time that cannot be scheduled against 30 July — so no session proposes it twice.

We are not only documenting what we did. We are documenting what we decided not to do, and why — because that is what an agent will otherwise quietly undo.

The standing instruction

The first thing in the context file is not a fact about the system. It is an instruction to every agent that reads it: when a decision is made or something changes, update the affected file in the same turn. It ships with a when X happens → update Y table — a requirement change updates the SRS and its revision history and its cross-references; a resolved question updates the decision log with the answer, because a closed issue with no recorded answer is not closed.

The result is a dated decision log (docs/TEAM-MEETING.md) recording the reasoning for every significant call across the project, and it is the reason a session opened on day 19 can be productive in its first minute.

Why the contract is human-owned

shared/src/contract.ts is written by a human once, before any agent runs, and given verbatim to every packet. An agent that wants to change it must stop and escalate to a person.

Rejected: letting each module's agent define the types it needs. Three agents produce three locally-reasonable, mutually incompatible Task types, each passing its own tests, and integration becomes a rewrite. Agents make this failure worse rather than better, because they generate plausible types faster than a human notices the three disagree.

03The architectural style

The style is a pure functional core inside an imperative shell, with the core reduced to a single function and its purity enforced structurally rather than by convention.

Three rules, and what each one buys

  1. There is exactly one scheduling engine. FR-SCH specifies a pure function — given a day's busy intervals and a task, return the valid slots. FR-RSC specifies when that same function is called again. Rescheduling is not a second algorithm. All three reschedule triggers — an inferred miss, a user-declared skip, a displacement — route through one service that re-invokes the one engine.
  2. The engine is pure: no clock, no database, no side effects. It declares an empty dependency block, permanently. An engine that cannot import anything cannot import a clock. That purity is what allows it to be property-tested over 1,000 randomized days with no database and no browser, and held to 100% coverage.
  3. Time is an integer Minute — minutes since local midnight. The engine never sees a Date. The convention is what makes purity structural rather than aspirational: there is no clock-shaped type in scope to reach for.
The failure this prevents

Ask an agent to implement FR-RSC-02 — repair the schedule when a commitment displaces a task — and it will write a tidy little findNextFreeSlot() inside the reschedule service, because locally that is the simplest correct thing to do. FR-RSC-03 is now false, the system has two placement algorithms that will diverge, and no test fails. Code review catches this on a hand-written codebase. With three agents out-generating three reviewers, it does not. §10 is the response.

04The architectural style, stated in a prompt

The style above is not left implicit for the agent to infer. Every packet restates the component obligations it is working inside, in the packet's own text: 

## Core components — the obligations this packet works inside

**Engine** (`engine/src`) — a PURE function. Given a schedulable day, a set of
busy intervals and a task, it returns ranked candidate placements. It reads no
clock, opens no socket, touches no database, and declares ZERO dependencies.
It is the ONLY function in this System that produces a placement.

**Reschedule service** (`server/src/reschedule`) — the POLICY layer. It decides
WHEN the engine is called again (miss inferred, skip declared, displacement)
and what to do with the result. It MUST NOT compute a placement itself; it
re-invokes the engine. (FR-RSC-03)

**Recommendation** (`server/src/recommendation`) — turns a Daily Metric Set into
a Recommendation via content-agnostic rules, then turns an ACCEPTED
recommendation into a real Task placed by the engine above. (FR-REC-04)

**Adapter** (`server/src/wearable`) — parses a vendor export into the Daily
Metric Set. One adapter per vendor; the rules never learn a vendor's shape.

### Files you must NOT touch
- `shared/src/contract.ts` — human-owned. If you need it changed, STOP and escalate.
- any file under a frozen test directory listed in `scripts/frozen-tests.json`.

Two things in that block are doing most of the work. The obligation is stated negatively — what the module must not do — because the positive form ("the reschedule service calls the engine") is satisfied by code that also does the forbidden thing. And the packet names the files it may not touch, which is the only instruction that survives an agent deciding it has a better idea.

05Requirements — the worked example

A web application combining an adaptive scheduling engine with real wearable health data.

Every commitment in a user's day — class, meeting, habit, workout, meal — is a task with a duration, a priority, a preferred time window and a flexibility flag. A single scheduling function places tasks around fixed commitments and re-invokes itself to repair the schedule when a task is missed, when the user declares one skipped, or when a new commitment displaces one. Separately, the system reads the user's Garmin data — sleep score and active calories — and adapts its recommendations: poor sleep lowers workout intensity, high activity raises the day's calorie target.

FR-REC-04 — the load-bearing requirement

A recommended workout is created as a task and placed by the same engine, subject to the same conflict detection and rescheduling as any user-created task.

This is what makes the project one integrated system rather than a scheduler and a fitness app sharing a login. If everything else shipped and FR-REC-04 did not, the project would have failed at its own thesis while appearing complete. The scope rule that follows is explicit in the context file: if the schedule forces a cut, cut anything else first.

Requirements are classified, and the classification is binding

Following IEEE 830 §4.3.4, every requirement is Essential, Conditional or Optional, and only Essential requirements are conditions of acceptance. SRS §2.7.1 defines a Core Demonstrable Capability — the irreducible set carrying the system's central claim — from which nothing may be cut.

On 26 July, with the presentation imminent, the team cut all remaining Conditional work definitively, recording the decision and its reasoning rather than letting it lapse quietly. Two Conditionals already shipped and tested (the .ics export, the month navigator) were kept: a forward-looking scope cut does not un-build sunk work.

Design constraints that shaped the build

  • CON-05 / §4.9 — the system is not a medical device. It does not estimate basal metabolic rate; it asks the user for a calorie baseline. The Garmin export contains a bmrKilocalories field, and using it is the most tempting trap in the file; the prohibition is written into the context file for that reason.
  • A dietary preference never relaxes — not at any point, for any reason, even when no compliant item can be found.
  • Workout and meal libraries are locally seeded, not runtime API calls. A push-up is the same push-up in July as in January. The consequence is that the entire acceptance demonstration runs with outbound network access disabled — and FR-LIB-02 requires us to prove that rather than assume it (§10).
  • CON-06 — the nineteen-day window. No Essential requirement may depend on a third party's approval. This is the single constraint behind the largest architectural decision in the project (§1).

06Process prescription

The process is test-driven, incremental, and split across two separate agent sessions per increment. The split is the load-bearing part. 

  RED session                human gate            GREEN session
  ───────────                ──────────            ─────────────
  sees: SRS + contract   →   a SECOND human    →   sees: the failing tests
  never: an implementation    reads every test       never: permission to edit one
        ↓                     against the SRS              ↓
  writes the test suite   →   FREEZE (sha256)   →   writes the implementation
  + one throwing stub         per file               until the suite is green

  If the GREEN agent believes a test is wrong, it STOPS.
  A human adjudicates it against the SRS. The agent may not edit,
  skip, rename or weaken a test — ever.

Why it cannot be collapsed into one pass "for speed"

When a single agent writes the test and the implementation together, the test encodes what the code does rather than what the requirement says. It goes green, it looks entirely reasonable, and it is wrong — and you find out on presentation day. This is not a prompting problem and cannot be fixed by asking the agent to be careful. It is structural, and the session split is the fix.

The freeze is content-addressed, not commit-based

Once a RED suite passes its human gate, npm run freeze records a sha256 per file in scripts/frozen-tests.json; npm run guard:tests-frozen re-hashes and compares on every build. Eight suites, 33 files, are pinned this way.

A commit-based freeze needs a repository and that commit reachable. Neither holds in a shallow CI checkout, and neither holds during a rebuild from the specification — which freezes its suites before it commits anything. A freeze that only works in the repository that created it cannot protect a rebuild, which is the case it most needs to protect. Hashing is also strictly stronger than the diff it replaced: it catches an edited test, an edited-and-committed test, a deleted test, and a file quietly added to a frozen suite.

The git sha is still recorded as provenance — it attests when the freeze happened, from something other than the manifest, and it is what catches a suite edited and then re-frozen to cover the edit.

The commit log is the third piece of project memory

After the documents and the specification. On an agentic project it is the only durable record of what an agent actually did — the session that wrote the code is gone, and the diff is what is left. A commit is therefore the unit of review, not the unit of work: one packet, one reviewable diff, one human who has read it. Every commit carries an Owner: trailer naming that person, and every behavior change carries a Requirements: trailer — a behavior change that cites no requirement is somebody's opinion. 203 commits, 20 of them explicit RED/GREEN boundary commits.

No AI credit lines appear on any commit, by team decision. Authorship of a commit is the human named in Owner:, because that trailer means "I read this diff and I can defend it," which is a thing only a person can assert.

08Verification and validation prescription

The V&V prescription is written into the packets as concrete, checkable obligations — not as an instruction to "test thoroughly." Three groups, in the order they were specified.

1 · Boundary and partition cases, enumerated in the specification

FR-SCH-09 ships an eight-row boundary table quoted verbatim into packet 04. These are input-domain partitions for the placement function, and the RED agent is required to write a test per row:

  • A gap exactly the task's duration — must be accepted.
  • A gap one minute short — must be rejected, and the scan must continue to the next gap rather than returning a partial fit or silently dropping the task.
  • A task whose preferred window is entirely occupied — must return ranked alternatives, not an empty result and not a failure.
  • Adjacent busy intervals that touch but do not overlap; an all-day commitment; a task that cannot fit anywhere in the schedulable day; ties in priority; ties in proximity.

Ranking is specified too, so it cannot be settled by whichever comparison the agent happened to write first: proximity to the preferred window, then earliest start (FR-SCH-03), with priority ties broken by creation instant (FR-SCH-10).

2 · Behavioral V&V — what must be true of the running system

  1. An occurrence whose window elapses with no completion must be classified missed by inference, without waiting to be told (FR-RSC-01) — and the classification must be a proposal the user can overturn, not a verdict: marking the original complete withdraws the system's own reschedule (FR-RSC-09).
  2. A fixed commitment dropped onto a flexible task must displace it and the schedule must repair itself, with the displacement stated in plain language rather than happening silently (FR-DSH-07).
  3. A fixed commitment must never be displaced to resolve a conflict (FR-CAL-03); a new fixed commitment landing on an existing one must be rejected, not silently overlapped.
  4. A recommended workout must be defended identically to a user task — the same displacement, the same repair, the same engine (FR-REC-04).
  5. An accepted recommendation that replaces a scheduled workout must be durable across a retrieval sweep — the replaced occurrence must not resurrect (FR-RSC-05/06).

09Incremental prompts — the anatomy of a packet

Every packet has the same eight parts, in the same order. The shape follows the course's house style — the Sandwich Method, Attention Anchoring, Visual Emphasis, Clear Delimiters, and Selective Context — and each part exists to close a specific failure we had seen or could name.

The escalations are the highest-value output

An ambiguity the RED agent found and refused to guess at is the most useful thing a packet produces, and it exists nowhere else once the session ends. Packet 04's escalations are recorded in its report and in the body of the freeze commit; several became requirement corrections in the SRS rather than assumptions in the code.

A packet is not finished when its code merges

It is finished when the prompt that produced it is on disk. We learned this on 30 July, during the final rehearsal: two packets had genuinely been run — the commits were in the history and the implementations existed — but the prompt text was never saved out of its session. A replay in numerical order would freeze two suites it then could not make green, and the pack's index listed one of them as done, naming a file that had never existed.

The pack had already named two failure modes: a prompt that does not exist is visibly missing; a prompt written from speculation is invisibly wrong. This was a third — written, used, and never saved is invisibly absent — and it is the worst of the three, because the code merges, the report gets filed, and the status table says done. Both packets were authored from the specification and the frozen suites (never from the committed implementation) and the pack now generates the system end to end again.

10Structure verification: prescription vs. produced code

An inspection-only requirement gets a test that enforces it, or it silently becomes false.

The specification marks four requirements (I) — verifiable by inspection. Inspection means a human reads the code and confirms a structural property holds. On this project that is exactly the check that does not scale, so each one was compiled into a script that runs in npm run verify and in CI on every push.

Note what each line says: every guard names the requirement it enforces, and several name the limit of what they check. The offline guard states in its own output that it performs the inspection half and that the offline demonstration is a rehearsal it does not perform. A guard that overstates its own scope is a guard that will be trusted for something it never checked.

The rule that makes a guard mean anything

A guard that has never been observed to fail does not count.

Before any guard is trusted, every individual check inside it is watched failing against a deliberately introduced violation, and the failing output is recorded in the packet's report. Packet 16b produced fourteen must-fail transcripts where eleven were required.

The reason is simple and it is not paperwork: a green guard that enforces nothing exits 0 exactly like a working one. From outside, the two are indistinguishable. This project has shipped that mistake twice and caught it both times, which is why the rule is written down rather than held as a good intention.

The guards are human-owned, like the contract

scripts/ is the second exemption from the rule that the pack generates everything, and it is earned by a distinct argument: you cannot verify a verifier with the thing it verifies. A regenerated guard that came back ten percent weaker is indistinguishable, from outside, from one that came back right — both exit 0. Every other packet is checked by something downstream; the guards are that something.

A guard may enter the build by exactly two routes: transcription (human-authored, copied in verbatim, like the contract), or generation from a human-authored specification with every individual check watched to fail. Five of the nine files in scripts/ are generated by that second route; four are transcribed. Neither route permits a check that has never been observed to fail.

Route 2 is, for the property at issue, the stronger of the two. The danger is a guard that enforces nothing while exiting 0 — route 2 tests that behaviorally, whereas transcription only attests to provenance. A hand-typed guard with a typo in its regex is inert, and nothing about having been typed by a human reveals it.

12Highest assurance: the property-based proof

The strongest correctness claim in the project is not a test case. It is a universally quantified property, checked by randomized generation over 1,000 independently constructed days. 

NFR-COR-01 — stated as a property, not as an example

  ∀ day ∈ SchedulableDays,
  ∀ busy ⊆ Intervals(day),
  ∀ task ∈ Tasks :

      ∀ slot ∈ findCandidateSlots(day, busy, task) :

          slot.duration = task.duration
        ∧ slot ⊆ day
        ∧ ∀ b ∈ busy : ¬ overlaps(slot, b)

  Checked over 1,000 randomly generated (day, busy, task) triples.
  fast-check shrinks any counterexample to a minimal failing case.

Why the property is checkable at all

Because the engine is pure. It takes data and returns data — no clock, no database, no network, no hidden state — so a thousand independent invocations need no fixtures, no teardown and no browser, and they run in about a second. The purity is not a stylistic preference; it is what buys the assurance level.

And the purity itself is established structurally rather than by inspection: the engine declares an empty dependency block (checked by guard:engine-deps), reaches no ambient global (checked by guard:engine-purity), and never sees a Date because time crosses its boundary as an integer Minute. Three independent mechanisms, none of which relies on anyone remembering.

The falsifiable claim this structure makes

Delete engine/src/, re-run packet 05, and the 30 frozen engine tests and the 1,000-case property still pass.

A differently-shaped implementation — a different gap-merging strategy, a different comparison order — must still satisfy the same specification in its executable form. That is the whole reason the tests are written first and frozen before any implementation exists. The implementation is disposable. The specification and its executable form are not.

13Demonstration

The SRS §6 acceptance scenario, performed against the running system on 30 July 2026 — real Express server, real MongoDB, real browser.

The figures below are captured from that run, in order. Each caption names the requirement being exercised. Act III is the project's central claim; the rest is the apparatus that makes it meaningful.

Act 0First contact

Registration captures the schedulable day and the calorie baseline. The baseline is asked for, never estimated — CON-05, and the reason the export's bmrKilocalories field is prohibited by name.

Act IThe engine places, and offers alternatives rather than failing

A flexible task is handed to the engine, which chooses the time. When the preferred window is already occupied, the engine returns ranked alternatives — it does not fail, and it does not silently drop the task.

Act IIReal wearable data changes the plan

A sleep score of 40 and 850 active calories are ingested. Two independent rules consume them — neither knows the other exists — and the day's recommendation changes: the intensity tier drops, and the calorie target rises off the baseline the user supplied at registration.

Act IIIThe claim — a recommendation becomes a real task, defended identically

This is the load-bearing sequence

FR-REC-04 says a recommended workout is created as a task and placed by the same engine, subject to the same conflict detection and rescheduling as any user-created task. Figures 11–14 show that clause performed rather than asserted: first the recommendation becomes a real placement, then a fixed commitment is dropped directly on top of it and the same engine displaces and re-places it.

Act IVThree triggers, one placement function

The schedule repairs itself from three different causes — a user-declared skip, an inferred miss, and a displacement. All three route through the same service into the same engine. And the inference is a proposal: the user can overturn it, and the system withdraws its own reschedule.

Act VThe rest of the surface

Real data, not synthetic

Separately from the scripted scenario above, 50 real daily metric sets from a teammate's own Garmin export were ingested through the adapter and the live API: real sleep scores driving real intensity tiers (14, 40, 37 → LOW; 76, 83 → HIGH) and real active calories driving real targets. This is what satisfies FR-WER-10, the requirement that a metric from a real device drives a real recommendation — the injection path used in Fig. 10 is synthetic by design and deliberately cannot satisfy it.

The export is a real person's health record. It never entered the repository: it was read from a local path, the ingestion ran, and the working copy was deleted. Test fixtures are derived from it, never copies of it.

14What the process caught, and what it did not

A verification story is only worth something if it includes the case where verification lost. Here is ours, from the final rehearsal.

The bug

While rehearsing the demonstration against the running server, applying a recommendation to tomorrow's schedule returned 409 — no workout above LOW to replace, for a workout that had plainly not started. The code asked placement.start <= clock.nowMinute(): a minute-of-day comparison carrying no calendar. It was wrong in both directions — a future date's workout read as already begun once the wall clock passed its start minute, and a past date's read as still upcoming whenever the clock had not reached it, so a finished day's history could be rewritten.

The honest part

507 passing tests did not catch it, because every frozen suite applies the recommendation to the clock's own date — the one configuration in which this bug is invisible. The acceptance transcript captured two days earlier was real, and it was also time-lucky. We found the bug by running the system, not by running the suite.

The failure mode compounds it: a 409 is indistinguishable from the system correctly having nothing to replace. Nothing looked broken.

What the process then did correctly

  • Fixed with a date-aware hasBegun(date, startMinute) mirroring the hasElapsed check the reschedule service had already grown for the same defect shape a day earlier — the same class of bug, in a class that never received the equivalent fix.
  • Pinned by three new tests in a new, unfrozen directory that imports the frozen acceptance harness, so the real engine and the real reschedule service run. Two of the three were watched failing against the pre-fix source first; the third pins the case that must keep refusing.
  • The requirement was corrected in place in the SRS (v2.41), with revision history — not silently patched in code while the document went on asserting the old behavior.
  • No frozen file was touched. All 8 freeze entries verified unchanged; 510 green.

Systematic testing tells you what you checked. It does not tell you what you forgot to check. That is why we still rehearse against a running server.

15Summary

  • Scale was managed by prescription and incrementality. A persistent context document that no session may let go stale, plus 28 ordered packets each sized to one agent session and one reviewable diff, kept a three-person team's agents from producing a codebase nobody understood.
  • Trust came from structure, not from reading the output. The RED/GREEN session split means no agent ever wrote both a test and the code it tests. The sha256 freeze means the specification's executable form cannot be weakened to make a build go green. Six guards mean the architectural prescription is checked mechanically on every commit — and every one of them was watched failing before it was trusted.
  • Quantitative targets were met and are reproducible in seconds. 100% engine coverage against a 90% threshold; 1,000 randomized days with no overlapping placement; 510 tests across five levels; all four inspection-only requirements enforced executably.
  • The system demonstrates its own central claim end to end. A real metric from a real device changes a recommendation, the recommendation becomes a real task on the real calendar, and that task is then displaced and repaired by exactly the same engine that defends everything else on the day.

Not a scheduler and a fitness app sharing a login. One system — where a recommendation is defended by the same logic as everything else on the calendar.

GapStatus
FR-WEL-04 is not satisfied. The seven-day wellness panel was removed at the requirement owner's request late in the build. Flagged, recorded as OPEN-37, and the SRS updated to say so — rather than letting the document assert a capability the build no longer has.

Two prompt packets have never been run. They were authored on 30 July from the specification and the frozen suites to close a hole in the pack (§9). What we would build next

  • Priority displacement (FR-SCH-07/08) — a higher-priority task able to move a lower-priority one rather than only fitting around it. Deliberately not started: it is the most seductive way to lose a week on a nineteen-day project.
  • A third metric — stress or HRV. The extensibility shape is guarded and demonstrated self-maintaining against a temporary third rule; the requirement that proves it by actually adding one (FR-REC-12) was cut for schedule.
  • The live Garmin Health API as a second adapter behind the same port, once partner approval is no longer on a nineteen-day critical path. The recommendation engine would not change — that is what the adapter seam was for.
